# Yoyo.Abp 9.x / 10.x 迁移治理设计

> 状态：待用户审阅  
> 目标：在保持当前 33 包兼容线稳定的前提下，显著缩短 `v9.4.2 / .NET 8` 与后续 `v10.x / .NET 9` 迁移收尾时间，并为后续产品面瘦身建立可验证的治理机制。

## 1. 背景

`Yoyo.Abp v7.4` 第一波迁移已经完成技术闭环：

- `proj-rename-ps` 已被纳入仓库并承担正式迁移职责；
- `v7.4` 生成、overlay、package smoke、下游 `YoyoBoot` / `Rider aspnet-core` restore-build smoke 已全部通过；
- 当前首波生产兼容线稳定在 33 个 `Yoyo.Abp.*` 包；
- 当前默认主键语义仍然是 `string`，这是与官方 upstream 的长期永久差异。

但是，`v7.4` 的闭环过程仍然暴露出一个核心问题：

> 当前迁移引擎虽然已经具备“能生成”的能力，但还不具备“面向跨代升级快速收尾”的治理能力。

这会在 `v9.x / .NET 8` 与 `v10.x / .NET 9` 中被进一步放大，因为上游变化不再只是目标框架切换，而是会叠加包面、认证模块、模板基础设施和依赖栈变化。

## 2. 已确认事实

### 2.1 当前兼容基线

- 当前兼容基线是 `codex/dev-7.3.0` 所代表的 Yoyo 产品线。
- 当前首波生产兼容面为 33 个 `Yoyo.Abp.*` 包。
- 当前下游生产消费者至少包括：
  - `C:\Code\yoyoboot\YoyoBoot`
  - `C:\Code\gitea\Rider\src\aspnet-core`
- 当前两个下游都能通过命令行覆写 `YoyoAbpVersion` 和本地 package source 的方式消费新生成包。

### 2.2 上游版本锚点

- 官方 `v9.0` 明确升级到 `.NET 8`。
- 官方 `v9.4.2` 位于 `.NET 8` 代际内，可作为 Yoyo 下一阶段首选目标输入。
- 官方 `v10.0` 明确升级到 `.NET 9`。
- 官方 `v10.3` 仍属于 `v10.x / .NET 9` 代际，不应被误判为 `.NET 10` 锚点。

### 2.3 上游结构变化信号

基于官方 release 信息，`v9.x / v10.x` 除了目标框架变化外，还已经出现以下类型变化：

- 认证相关项目变化，例如 `Abp.ZeroCore.IdentityServer4` 的移除；
- 模板和基础设施变化；
- NuGet 依赖整体升级；
- 运行时/配置行为细节变化，例如租户 header 命名调整。

因此，后续迁移不能再用“换 SDK + 跑脚本 + 人工捡雷”的方式推进。

### 2.4 `Log4Net` 的当前状态

`Yoyo.Abp.Castle.Log4Net` 当前仍然是真实产品资产，而不是已经可无脑删除的历史包：

- 它仍然在当前 33 包打包清单中；
- 主仓内仍有独立源码、测试和打包路径；
- `YoyoBoot` 仍然直接引用 `Yoyo.Abp.Castle.Log4Net`；
- `Rider aspnet-core` 的主 WebHost 已大量使用 `Serilog`，但 `Migrator` 仍保留 `UseAbpLog4Net()` 和 `Yoyo.Abp.Castle.Log4Net` 引用。

结论是：

> `Log4Net` 已经是高优先级退役候选，但当前还不是“可直接从 33 包兼容线移除”的状态。

## 3. 设计目标

本设计要解决的问题不是直接实施 `v9.x / v10.x` 升级，而是定义一套可复用的治理模型，使下一轮迁移具备以下特征：

1. `proj-rename-ps` 从脚本集合升级为“版本感知的迁移引擎”；
2. `v9.4.2 / .NET 8` 升级以当前 33 包兼容线为首要目标；
3. 包面瘦身与升级主线解耦，避免把两个高风险动作绑定到一个交付中；
4. 将差异分析、回归防护、包面校验和下游消费验证前移到迁移流水线本身；
5. 为 `v10.x / .NET 9` 和后续更高代际迁移建立可延续的门禁机制。

## 4. 非目标

本设计明确不做以下事情：

- 不立即实施 `v9.4.2` 或 `v10.x` 代码迁移；
- 不在第一阶段重写全部 PowerShell 迁移逻辑为 C# 或 AST 工具；
- 不在 `v9.x` 首波中直接删除 `Log4Net` 等候选包；
- 不在一个交付内同时完成“跨代升级 + 包面瘦身 + 全部下游改造”；
- 不将 `v10.x / .NET 9` 与未来 `.NET 10` 路线混为一谈。

## 5. 总体策略

### 5.1 主策略：兼容优先、双轨治理

推荐采用以下主策略：

- **升级主线**：先以当前 33 包兼容线稳定打通 `v9.4.2 / .NET 8`；
- **瘦身支线**：并行建立产品面清理候选池，但不与首波升级交付强绑定；
- **共同门禁**：两条线共用同一套包面、差异、回归和下游消费验证机制。

这样做的核心原因是：

$$
\text{升级稳定性} > \text{一次性清理彻底性}
$$

对于当前项目，先缩短升级收尾时间，比先把包面做得更“漂亮”更重要。

### 5.2 为什么不推荐“升级与瘦身并行”

虽然同步清理 `Log4Net` 等候选包在理论上更干净，但会显著增加一次性交付复杂度。届时出现失败时，很难迅速判断问题属于：

- 上游版本变更；
- 迁移引擎规则缺口；
- 包面清理导致的下游引用断裂；
- 下游自有基础设施差异。

因此，首波 `v9.x` 不应承担产品面瘦身任务。

## 6. `proj-rename-ps` 强化设计

### 6.1 工具定位升级

`proj-rename-ps` 的定位升级为：

> Yoyo.Abp 的版本感知迁移引擎（migration engine）。

它的成功标准不再是“脚本跑完”，而是：

> 产物通过了包面、回归、打包和下游消费的完整门禁。

### 6.2 四阶段迁移模型

#### Stage A：输入归一化

职责：

- 识别输入 upstream 版本及其代际；
- 预扫描 target framework、关键项目、认证模块和打包配置变化；
- 输出“升级雷达”报告，而不是直接开始重写。

目标：

- 在迁移前回答“这次 upstream 与上一轮相比，根本变了什么”。

#### Stage B：语义迁移

职责：

- 执行 `string` 主键语义改写；
- 执行 `Yoyo.Abp.*` 包名与程序集名改写；
- 注入必须存在的补丁文件；
- 保持当前已验证的高风险修复（例如 Office 相关回归保护）。

要求：

- 现有规则继续保留，但按规则组显式分类，至少区分：
  - `package-identity`
  - `string-key-semantics`
  - `framework-cleanup`
  - `zero-and-auth-fixes`
  - `test-and-sampleapp-fixes`

#### Stage C：产品面收敛

职责：

- 根据显式 profile 决定保留项目；
- 生成 pack 清单；
- 校验 legacy 包和已废弃兼容层不得回流。

第一阶段只定义一个正式 profile：

- `profile-33-compat`

其含义是：

- 当前仍以 33 包生产兼容线为准；
- 上游项目新增/删除不能自动改变 Yoyo 产品面；
- 包面变化必须通过显式产品决策触发。

#### Stage D：验证出口

职责：

- 运行 validator；
- 执行 restore/build；
- 执行 package smoke；
- 执行 downstream consumer smoke；
- 输出结构化执行报告。

目标：

- 把“下游是否真的可用”从人工补充动作前移为迁移引擎正式出口。

### 6.3 第一阶段必须强化的五项能力

#### 1. 规则清单化

至少把以下内容从脚本正文中抽出或集中化：

- 33 包产品面清单；
- legacy 禁入包清单；
- 已知高风险回归清单；
- 规则组名称与执行顺序；
- 不同版本代际对应的启停规则。

#### 2. 版本感知

必须允许引擎显式区分：

- `v7.x / .NET 6`
- `v9.x / .NET 8`
- `v10.x / .NET 9`

并根据版本代际激活不同规则或不同风险提示。

#### 3. 差异报告

每次执行后都要输出至少四类差异：

- 项目面差异；
- 包依赖差异；
- target framework / build 资产差异；
- 下游潜在影响点。

#### 4. fail-fast 前移

在 restore/build 之前就应阻断以下结果：

- 包面漂移；
- legacy 包回流；
- `.NET Framework` / portable fallback 残留；
- 已知高风险回归；
- 下游固定版本绑定缺口。

#### 5. 下游验证模板化

当前至少固化两个下游模板：

- `YoyoBoot`
- `Rider aspnet-core`

模板应支持：

- 覆写 `YoyoAbpVersion`；
- 指向本地 package source；
- restore/build smoke；
- 输出首个真实 blocker。

## 7. 版本路线设计

### 7.1 Phase 1：`v9.4.2 / .NET 8` 首波兼容升级

目标：

- 在不改变当前 33 包兼容面的前提下，打通 `v9.4.2` 的标准迁移路径；
- 把 `v7.4` 阶段形成的验证链路提升到 `.NET 8` 代际；
- 识别 upstream 在认证、ZeroCore 和模板上的关键变化，但不在第一波中引入额外产品面收缩。

成功定义：

- `profile-33-compat` 能生成完整产物；
- validator 通过；
- package smoke 通过；
- `YoyoBoot` / `Rider` smoke 通过或首个 blocker 可清晰归因；
- 所有新问题都被归类为“引擎规则缺口”而不是“随机人工修复”。

### 7.2 Phase 2：`v9.x` 稳定后的退役候选治理

目标：

- 建立“候选包退役账本”；
- 对 `Log4Net` 这类已部分被替代、但仍保留消费点的包进行消费点归零验证；
- 只有在主仓、下游和 smoke 都不再依赖时，才允许真正移出兼容面。

候选池首批建议至少包含：

- `Yoyo.Abp.Castle.Log4Net`
- 未来可能被上游移除或下游替代的认证/桥接类包

### 7.3 Phase 3：`v10.x / .NET 9` 升级

目标：

- 以 `v9.4.2` 稳定产物为前置基线，进入 `v10.x / .NET 9`；
- 复用已经版本化的迁移引擎、差异报告和下游 smoke 模板；
- 在确认认证、包依赖和 header/config 行为变化后，再决定是否把“兼容升级”与“产品面瘦身”合并推进。

原则：

- `v10.x` 仍然先按兼容优先推进；
- 只有在 `v9.x` 已稳定且退役候选治理已有证据时，才考虑收缩产品面。

## 8. 产品面治理设计

### 8.1 当前原则

当前 33 包兼容线继续作为唯一正式兼容基线。

任何包的移除，都必须同时满足：

1. 主仓 pack 清单不再需要；
2. 主仓测试或 smoke 不再依赖；
3. `YoyoBoot` 不再依赖；
4. `Rider aspnet-core` 不再依赖；
5. 必要替代方案已经明确并完成 smoke；
6. 删除行为被记录为显式产品决策。

### 8.2 `Log4Net` 的设计结论

`Yoyo.Abp.Castle.Log4Net` 当前应被标记为：

> 退役候选，高优先级审计对象，当前不删除。

原因：

- `YoyoBoot` 仍有包引用；
- `Rider` 的 `Migrator` 仍有直接消费；
- 主仓仍存在独立源码和测试；
- 当前更适合作为“消费点清零专项”，不适合与 `v9.x` 兼容升级绑在一起。

### 8.3 退役候选账本

后续应为每个候选包记录以下信息：

- 包名；
- 当前主仓依赖点；
- 下游依赖点；
- 替代技术栈；
- 最小清理步骤；
- 删除前验证门槛；
- 删除后回滚方案。

## 9. 错误处理与验证设计

### 9.1 错误分类

后续迁移中的失败必须被归类，而不是统称“build 挂了”。最少分为：

- upstream 结构变化；
- 迁移规则缺口；
- 包面/pack 清单漂移；
- 固定版本绑定问题；
- 下游 API break；
- 运行时/配置行为变化。

### 9.2 最小验证矩阵

每次迁移候选至少通过：

1. 输入扫描报告；
2. 迁移输出 validator；
3. 主仓 restore/build；
4. package smoke；
5. `YoyoBoot` restore/build；
6. `Rider aspnet-core` restore/build；
7. 高风险专项回归检查。

### 9.3 成功定义

迁移候选的“成功”定义为：

$$
\text{成功} = \text{生成成功} + \text{验证成功} + \text{下游可消费} + \text{问题可归因}
$$

## 10. 风险与应对

### 风险 1：继续把脚本修改当作临时补丁

应对：把规则组、包面、legacy 禁入项和回归项显式化，并让执行报告成为正式产物。

### 风险 2：`v9.x` 首波就混入包面瘦身

应对：坚持 `profile-33-compat`，先把升级链路跑稳，再进入退役候选治理。

### 风险 3：误以为 `Log4Net` 已无使用价值

应对：以主仓 + `YoyoBoot` + `Rider` 的真实消费证据为准，而不是只看单一项目是否已转向 Serilog。

### 风险 4：`v10.x` 被当作 `.NET 10`

应对：明确 `v10.x` 只属于 `.NET 9` 路线评估，未来 `.NET 10` 等待 upstream 明确锚点。

### 风险 5：下游 smoke 再次退化成“最后补跑”

应对：将下游 smoke 模板化并放入迁移流水线正式出口，不允许只凭主仓成功就宣告升级通过。

## 11. 设计结论

本设计最终确认：

1. `proj-rename-ps` 必须继续强化，而且强化方向应是“治理能力升级”，不是继续无边界堆字符串替换；
2. `v9.4.2 / .NET 8` 应作为下一阶段首要目标，并继续沿用当前 33 包兼容线；
3. `v10.x / .NET 9` 必须在 `v9.x` 稳定后推进，不能和 `.NET 10` 混淆；
4. 产品面瘦身必须与首波跨代升级解耦；
5. `Yoyo.Abp.Castle.Log4Net` 当前属于高优先级退役候选，但暂不从兼容面删除；
6. 后续迁移成功的核心不再是“脚本能跑完”，而是“迁移引擎能稳定输出可验证、可消费、可归因的结果”。

## 12. 下一步

在用户审阅本设计并确认后，下一步只应进入**实施计划编写**，而不直接开始改代码。实施计划应至少覆盖：

1. `proj-rename-ps` 的规则清单化和版本感知改造；
2. `profile-33-compat` 的正式定义；
3. `v9.4.2 / .NET 8` 输入扫描与差异报告；
4. 下游 smoke 模板化；
5. `Log4Net` 退役候选账本的建立；
6. `v10.x / .NET 9` 的前置门禁条件。
