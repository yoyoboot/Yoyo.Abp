# Yoyo.Abp Upstream Sync Design

> 状态：已根据 `release/7.4` 审计优先策略与 `v9.4.2 / .NET 8` 主推荐路线修订，待用户 review；review 前不进入实现。

## 1. 背景与目标

`Yoyo.Abp` 是 `aspnetboilerplate/aspnetboilerplate` 的 fork，当前已形成明确的长期分叉语义：默认实体主键体系采用 `string`，并伴随一组需要长期保留的自定义修改。当前仓库与下游 `C:\Code\yoyoboot\YoyoBoot\` 仍主要停留在 `.NET 6` 代际，因此升级策略不能简单理解为“直接追最新 upstream”，而应先完成 `.NET 6` 代际收敛，再决定下一跳版本。

本轮设计修订后，目标调整为：

1. 以 `Yoyo.Abp 7.3.0.12` 作为 **Yoyo 现实基线**；
2. 先对齐官方最后一个 `.NET 6` 代际版本，即 `aspnetboilerplate v7.4`，并形成稳定的 `release/7.4`；
3. 在讨论合并前，先对 `release/7.4` 与 `codex/dev-7.3.0` 做 **代码差异审计** 与 **NuGet 清单审计**，用审计结果校正设计；
4. 在审计结论成立后，将后续主推荐下一跳调整为 **官方 `v9.4.2` / `.NET 8`**，而不是把 `.NET 7 / v8.x` 作为必经执行阶段；
5. 对 `IdentityServer4 / vNext / OpenIddict` 的处理严格区分“上游首次出现/并存”与“最终替换完成”两个时间点，避免过早删改；
6. 全程保持 `string` 主键语义及既有关键自定义修改不丢失；
7. 在更高版本路线稳定后，再评估是否继续推进到 `v10.3`，并在最终收口阶段移除面向 **`.NET Framework` 与低于 `.NET 6`** 的兼容内容，使支持矩阵收敛为 **`.NET 6+`**。

## 2. 已确认的关键事实

### 2.1 当前 Yoyo.Abp 基线

- 当前 Yoyo 工作基线：`7.3.0.12`
- 当前仓库以 `.NET 6` 为主要稳定运行时代际
- 当前公开发包体系使用 `Yoyo.Abp.*` 包名
- 当前版本语义存在“官方基线版本 + Yoyo 补丁尾号”的实际使用方式

### 2.2 官方 upstream 版本断点

已确认的上游版本代际与关键点为：

- `v7.4`：最后一个 `.NET 6` 代际稳定点
- `v8.0`：`.NET 7` 代际入口
- `v9.0`：`.NET 8` 代际入口
- `v9.4.2`：当前设计中更适合作为 `.NET 8` 主推荐稳定落点
- `v9.2.0`：上游已出现 `OpenIddict` integration packages
- `v10.0`：`.NET 9` 代际入口
- `v10.3`：当前最新公开 release

因此，本设计不再把 `v8.x` 视为必须落地的执行阶段，而是将其降级为 **差异分析参考点**；当前主推荐下一跳是 `v9.4.2`。

### 2.3 `release/7.4` 审计的初步观察

基于当前已完成的只读审计，已有以下初步结论：

- `release/7.4` 相对 `codex/dev-7.3.0` 的差异并非单点补丁，而是一次 **upstream 对齐 + Yoyo 永久差异回放**；
- 差异热点主要集中在：
	- `src/Abp.Zero.Common/*`
	- `src/Abp.Zero/*`
	- `src/Abp.ZeroCore/*`
	- `src/Abp.EntityFramework.Common/*`
	- `src/Abp.EntityFrameworkCore.EFPlus/*`
	- `src/Abp.AutoMapper/*`
	- `test/Abp.Tests/*`
	- `test/Abp.EntityFrameworkCore.Tests/*`
	- `test/Abp.ZeroCore.SampleApp/*`
	- `test/Abp.ZeroCore.Tests/*`
- `NuGet` 打包清单层面，`release/7.4` 与 `codex/dev-7.3.0` 的项目集合变化不大；当前更显著的变化是：
	- `nupkg/pack.ps1` 从依赖当前目录的脚本，调整为基于 `$PSScriptRoot` 的稳定入口；
	- `pack.ps1` 加入了显式失败检测，避免“有编译错误但脚本仍返回成功”；
	- 打包脚本新增了 `Abp.ZeroCore.NHibernate`；
	- `IdentityServer4` 与 `vNext` 四个包在 `7.4` 基线上仍全部保留。

这些观察意味着：**`release/7.4` 当前更适合作为稳定审计基线，而不是立即并回 `codex/dev-7.3.0` 的默认结果。**

### 2.4 fork 的核心长期差异

当前已确认的核心长期差异包括但不限于：

- `IEntity` 默认主键语义为 `string`
- `IRepository<TEntity>` 默认主键语义为 `string`
- 与 `string` 主键直接耦合的实体、仓储、EF/EFCore 生成器、Zero 体系类型
- 用户已明确要求：**已有关键自定义修改均需保留**

### 2.5 认证模块的生命周期判断

已确认的新增约束与修正如下：

- 若 upstream 某一代删除 `IdentityServer4` 相关项目，Yoyo 原则上同步移除，不将其视为永久保留差异；
- 若 upstream 后续再删除 `vNext` 相关项目，Yoyo 原则上同步移除；
- 但设计上必须区分：
	1. **`OpenIddict` 何时在上游首次出现**；
	2. **旧认证线何时在上游被完全替换完成**；
- 当前已知：`OpenIddict` integration packages 在官方 `v9.2.0` 就已出现，因此不能再把“`v10.3` 才出现 OpenIddict”作为设计前提；
- `v10.3` 更适合作为“进一步收口与替换完成”的候选观察点，而不是 OpenIddict 路线的唯一起点。

因此，`IdentityServer4 / vNext / OpenIddict` 在本设计中被定义为：**跟随 upstream 生命周期变化的兼容模块族，而不是 Yoyo 必须永久保留的 fork 核心差异。**

### 2.6 终态支持矩阵目标

已确认的长期约束如下：

- 在更高版本路线稳定后，Yoyo 不再继续保留面向 `.NET Framework` 的兼容内容；
- 终态支持矩阵应只覆盖 **`.NET 6` 及以上** 运行时；
- 仓库内仍为 `.NET Framework` 或低版本运行时保留的 `TargetFramework` / `TargetFrameworks`、条件编译、文档说明、打包项与脚本分支，都应进入最终清理范围。

## 3. 设计结论

### 3.1 总体路线

本次同步路线调整为“**先审计 7.4，再决定 merge 与下一跳**”的结构。

#### 第一稳定落点

- 基线：`Yoyo.Abp 7.3.0.12`
- 对齐目标：官方 `v7.4`
- 当前结果：`release/7.4` / `7.4.0.1`
- 当前职责：**稳定审计基线**，不是默认立即合并基线

#### 当前主推荐下一跳

- 基线：完成审计并确认设计后的 `release/7.4`
- 对齐目标：官方 `v9.4.2`
- 目标运行时：`.NET 8`
- 建议对外版本风格：可延续为 `9.4.2.1`

#### 延后决策点

- `v10.x / v10.3` 不再作为当前主推荐的立即执行目标；
- 是否继续推进到 `v10.3`，应在 `v9.4.2` 稳定后再做新一轮设计评审。

#### 参考分析点

- `v8.x / .NET 7`：作为差异分析与变更来源参考点保留；
- 不要求把 `v8.x` 作为当前执行主线的独立里程碑。

### 3.2 设计原则

1. **先审计，再讨论 merge**：`release/7.4` 先作为稳定审计基线，而不是默认立即合并回 `codex/dev-7.3.0`。
2. **代码差异与 NuGet 清单双轨审计**：同时评估运行时变化与发包边界，避免只看代码或只看包名得出片面结论。
3. **永久差异要显式建账**：`string` 主键体系及其他保留修改必须形成可追踪的补丁账本。
4. **把 `.NET 7` 降级为参考点**：`v8.x` 不再作为当前主推荐执行路径，而是为 `7.4 -> 9.4.2` 路线提供差异解释。
5. **区分认证模块的“首次出现”与“最终替换完成”**：OpenIddict 在上游的出现时间点与旧模块完全退出时间点，不应混为一谈。
6. **公开版本少，内部判断细**：当前对外/对内都应先形成 `7.4` 审计结论，再决定 `9.4.2` 及以后版本的实际执行方式。
7. **终态只保留 `.NET 6+` 支持面**：旧运行时兼容内容的清理放在高版本稳定后的最终收口阶段。

## 4. 方案对比

### 方案 A：先合并 `release/7.4`，再回头做设计与包审计

**优点**：
- 表面推进快
- 代码先落入主线，后续操作集中

**缺点**：
- 会把“设计是否合理”与“合并是否顺利”混为一体
- 一旦 merge 后再发现包袱判断有误，回滚成本更高
- 不利于澄清哪些改动是永久差异、哪些只是 `7.4` 阶段兼容保留

**结论**：不推荐。

### 方案 B：完成 `7.4` 审计后立即 merge，再推进 `v9.4.2`

**优点**：
- 比方案 A 稳妥，先有设计判断再做 merge
- 能较快形成统一基线

**缺点**：
- 审计完成后仍可能发现“merge 并不是当前最优动作”，例如更适合先做隔离桥接
- 把“是否 merge”过早固定为审计后的默认结果

**结论**：可作为备选。

### 方案 C：先把 `release/7.4` 作为审计基线，修订设计后再决定 merge，并将 `v9.4.2` 设为主推荐下一跳

**优点**：
- 最符合当前用户目标：先验证设计，再决定整合方式
- 能明确回答“当前改造是不是合适”和“哪些包可能进入后续移除候选池”
- 避免把 `.NET 7` 作为必须执行的中间站

**缺点**：
- 过程比“先 merge”多一步审计归类
- 需要在文档中重新界定 `v10.3` 的优先级

**结论**：**推荐，作为本设计采用方案。**

## 5. 分阶段设计

### Phase 0：升级前治理

目标：不改框架行为，只建立治理基础。

输出物：

1. upstream remote 与工作区策略
2. fork 差异账本
3. 高风险模块清单
4. 基线验证快照

重点关注区域：

- `Abp` 基础实体/仓储抽象
- `Abp.EntityFramework` / `Abp.EntityFrameworkCore`
- `Abp.Zero.Common` / `Abp.ZeroCore`
- `IdentityServer4 / vNext / OpenIddict` 相关项目及其迁移边界
- 与 `string` 主键耦合的测试和帮助器

### Phase 1：`7.3.0.12 -> 7.4.0.x`

目标：形成最后一个 `.NET 6` 代际的稳定 Yoyo 版本。

建议顺序：

1. 以官方 `v7.4` 建立纯 upstream 基线；
2. 对照当前 `7.3.0.12` 提炼永久差异与历史差异；
3. 仅回放必须长期保留的 Yoyo 修改；
4. 形成可编译、可测试、可发包的 `7.4.0.1`；
5. 将其冻结为 `release/7.4`。

### Phase 1.5：`release/7.4` 审计与设计校准

目标：在讨论 merge 前，验证 `release/7.4` 是否真的符合 Yoyo 的长期设计方向。

本阶段至少产出：

1. **代码差异审计摘要**：比较 `release/7.4` 与 `codex/dev-7.3.0` 的模块级差异；
2. **NuGet 清单审计摘要**：比较两边的 `nupkg/pack.ps1`、发包项目列表与关键包面边界；
3. **候选移除池**：把当前包/模块划分为：
	 - 永久差异支撑项
	 - `7.4` 阶段兼容保留项
	 - 在 `v9.4.2` 时优先复审的候选移除项；
4. **设计修订结论**：把审计结果回写到设计与实施计划。

冻结标准：

- 完成审计后，才讨论是否将 `release/7.4` 合并回 `codex/dev-7.3.0`；
- 未完成审计前，`release/7.4` 视为稳定审计基线，而非默认 merge 源。

### Phase 2：以 `v9.4.2 / .NET 8` 为主推荐的桥接分析与实施

目标：在 `7.4` 审计成立后，以 `v9.4.2` 作为当前主推荐升级落点。

本阶段的设计要求：

- `v8.x / .NET 7` 只作为差异分析参考，不要求单独形成当前执行主线；
- 重点回答：
	- `7.4 -> 9.4.2` 需要跨过哪些框架与包版本变化；
	- `string` 主键永久差异在 `.NET 8` / `v9.4.2` 上的重放点有哪些；
	- 认证模块在 `v9.4.2` 时处于何种并存状态；
	- 哪些 `7.4` 阶段兼容保留项在 `v9.4.2` 可以进入移除候选。

### Phase 3：形成 `9.4.2.x` 主稳定落点

目标：在官方 `v9.4.2` 基线上完成 Yoyo 永久补丁回放，并形成当前主推荐的 `.NET 8` 稳定落点。

这一步完成后，路线含义变为：

- Yoyo 不再停留于 `.NET 6` 最后一代；
- 已有一个更现代、但仍低于 `.NET 9` 的稳定对齐点；
- 是否继续到 `v10.3`，应基于此落点再次评审。

### Phase 4：评估 `10.x / 10.3` 是否继续推进

目标：在 `v9.4.2` 稳定后，再决定是否继续向 `.NET 9 / v10.x` 推进。

重点问题包括：

- `v10.x` 对 Yoyo 当前使用面是否有足够收益；
- 认证模块在更高版本的替换完成度与迁移成本；
- 是否值得把 `.NET 9` 作为下一阶段底座。

### Phase 5：升级完成后的 `.NET Framework` 清理与支持矩阵收口

目标：在高版本路线稳定后，正式移除仓库中面向 `.NET Framework` 与低于 `.NET 6` 的兼容内容，确保终态只保留 `.NET 6+`。

该阶段重点包括：

- 清理项目文件中的 `net4xx` / 旧运行时 target；
- 清理 `NETFRAMEWORK` 或等效的历史兼容条件分支；
- 清理仅为 `.NET Framework` 保留的打包、构建、文档与样例说明；
- 重新验证解决方案、测试矩阵与打包结果只面向 `.NET 6+`。

## 6. 分支、Tag 与工作区策略

### 6.1 基线分支策略

用户已明确提出：以 `7.3.0.12` 为现实基线，同时先审计 `release/7.4` 对当前旧线的影响。对此本设计确认如下：

- **Yoyo 现实基线**：`codex/dev-7.3.0`
- **稳定审计基线**：`release/7.4`
- **当前主推荐下一跳**：`sync/9.4.2-yoyo`（名称可调整，但目标语义不变）

也就是说：不是直接放弃 `7.3.0.12`，而是先拿它与 `release/7.4` 做审计，再决定 merge 和后续升级动作。

### 6.2 推荐分支结构

- `mirror/upstream-v7.4`：纯 upstream `v7.4` 基线
- `sync/7.4-yoyo`：在 `v7.4` 上回放 Yoyo 差异
- `release/7.4`：`7.4.0.x` 稳定审计基线
- `audit/7.4-vs-dev-7.3.0`：可选，用于承载代码差异 / NuGet 清单审计产物
- `sync/9.4.2-yoyo`：当前主推荐下一跳工作分支
- `analysis/v10.x-decision`：后续是否推进 `v10.x / v10.3` 的评审分支

### 6.3 Tag 规则

维持当前数字尾号风格：

- `7.4.0.1`
- `7.4.0.2`
- `9.4.2.1`（建议）

不强制切换为 `v7.4-yoyo.1` 之类命名。

## 7. 风险设计

### 风险 1：在审计前过早 merge，导致设计与实现纠缠

**表现**：尚未证明 `release/7.4` 的改造方向完全正确，就先合并回 `codex/dev-7.3.0`。

**应对**：把 `release/7.4` 固定为稳定审计基线；先完成审计，再决定 merge。

### 风险 2：Yoyo 历史补丁无法按提交粒度干净回放

**表现**：现有自定义差异与历史小修混杂。

**应对**：按“语义块”而不是按“提交顺序”重建补丁账本。

### 风险 3：默认主键语义在高版本中被 upstream 默认约定反复冲击

**表现**：官方默认仍是 `int`，你方默认是 `string`。

**应对**：把该语义视为长期永久补丁位，集中治理，不把它当成一次性 merge 冲突处理。

### 风险 4：过早删除当前仍有价值的包或认证模块

**表现**：仅凭 `pack.ps1` 或表面项目名判断“看起来可以删”，导致运行时或样例/测试断裂。

**应对**：通过代码差异 + NuGet 清单双轨审计，把包/模块分为“永久支撑 / 阶段保留 / 候选移除”三类，移除动作推迟到更高版本评审阶段。

### 风险 5：把 OpenIddict 的首次出现与最终替换完成混为一谈

**表现**：错误地把 `v10.3` 当成 OpenIddict 的唯一起点，导致对 `v9.x` 认证线的判断失真。

**应对**：在设计里显式区分“首次出现时间点”与“最终替换完成时间点”。

### 风险 6：移除 `.NET Framework` 兼容层可能引发残余脚本、文档与多目标构建断裂

**表现**：即便主项目已升级完成，仓库中仍可能残留老的 `TargetFrameworks`、条件编译、打包逻辑或文档说明，导致“名义上升级完成、实际上仍背负旧运行时兼容”。

**应对**：把“.NET Framework 清理”单独作为最终收口阶段，而不是零散夹在升级过程中处理；通过全仓扫描与终态验证，确保最终支持矩阵明确收敛到 `.NET 6+`。

## 8. 验证设计

### 第一阶段验证（`release/7.4` 审计）

建议至少覆盖：

- 核心基础层测试结果回顾
- `release/7.4` 与 `codex/dev-7.3.0` 的模块级代码差异分类
- `pack.ps1` 项目清单差异与发包边界判断
- `IdentityServer4 / vNext` 当前包面保留状态确认
- `string` 主键语义回归验证证据

### 第二阶段验证（`v9.4.2`）

除以上外，还需增加：

- `.NET 8` / 目标框架适配验证
- 关键项目编译与测试矩阵验证
- 版本号与包输出一致性验证
- 认证模块在 `v9.4.2` 的实际并存/替换状态验证

## 9. 本设计的最终结论

本次路线修订后，当前正式定义为：

1. 以 `Yoyo.Abp 7.3.0.12` / `codex/dev-7.3.0` 作为 Yoyo 现实基线；
2. 先把 `release/7.4` 视为稳定审计基线，而不是默认立即 merge 的分支；
3. 通过 `release/7.4` 与 `codex/dev-7.3.0` 的代码差异审计 + NuGet 清单审计，验证现有改造是否符合长期方向；
4. 在审计结论成立后，将后续主推荐升级目标调整为 `v9.4.2 / .NET 8`；
5. 将 `v8.x / .NET 7` 降级为参考分析点，而不是当前执行主线；
6. 对 `IdentityServer4 / vNext / OpenIddict` 按 upstream 生命周期进行更精确的阶段判断，不再把 OpenIddict 路线错误地绑定为仅在 `v10.3` 才出现；
7. 在更高版本路线稳定后，再决定是否推进到 `v10.3`，并最终清理 `.NET Framework` 与低版本运行时兼容内容，使仓库只保留 `.NET 6+` 支持面。
